# Development preview: collective petition foundation

Runtime commit: `36f8fc4`. Preview Worker version: `eec4b62e-d5c5-4c55-b1a6-9964dc84721a`, verified serving 100% of preview traffic on 2026-10-13.

Kindle collective petitions have bounded plain-text titles and demands, one publication during a citizen's seven-real-day window, one verified human signature per petition, immutable request receipts, and exact expiry guards. Publishing includes the author's signature. The weekly-active verified-human census and rounded-up three-percent threshold are captured atomically in publication SQL, then remain fixed for that petition. Threshold crossing is latched once and survives expiry, reopening and population changes. The API explicitly projects public petition records plus the requesting citizen's own participation flags; it never returns citizen identities or signature lists. Request fields cannot grant eligibility, choose a foreign namespace, alter deadlines/thresholds, or post Cabinet responses.

The existing trusted Tier-1 verification provider remains absent. Live publication and signing therefore fail closed. Only fresh trusted email/unique-phone evidence can enter the human activity ledger; game AI actors have no path into it. The application can read actual Cabinet response records, but no Cabinet publishing interface or live AI response service was introduced. Daily policy-priority requests remain separate from the collective petition mechanism and were relabeled accordingly. A collective signature locks citizenship both in serialized status and in the atomic enrollment write.

The Civic interface shows progress, seven-day timers, signed/expired/awaiting/recorded-response states and linked verification reasons. Interrupted submissions retain the same receipt, block editing and conflicting commands, and allow an identical retry. Stale refreshes and foreign response namespaces cannot replace current state. The persistent inbox now derives near-threshold alerts from recorded Kindle petitions and response updates for petitions the citizen started or signed. Ballot alerts remain unavailable.

Validation: 218 Node tests, 93 SQL tests, lint, TypeScript and build passed. Actual SQLite/API fixtures cover duplicate signatures, threshold rounding/latching, expiry boundaries, persistence, concurrent publications, request collisions without orphan records, foreign/unverified/forged requests, population eligibility, public projection, response integrity, and citizenship locking. UI fixtures cover disabled direct-handler guards, immutable retry, foreign response rejection and honest response states. Desktop/mobile screenshots of isolated component fixtures show contained controls, progress and verification explanations, with no horizontal overflow. Fixture timers are labeled as fixtures; live countdown logic is separately covered by the shared timer tests.

Live verification: anonymous reads return HTTP 401 and `Cache-Control: private, no-store`. The normal public world read initialized the additive tables without manual data migration or reset. Subsequent read-only D1 checks confirmed all three civic tables exist, with zero live petitions, zero signatures and zero verified visits. No live petition, chat, presence, ballot, trade, meal or work command was submitted; no shift was claimed.

Its earlier threshold-alert gap now has an authoritative foundation. Production, docs hosting, credentials and existing citizen ledgers were preserved.
